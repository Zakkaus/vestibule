# 这个机器人手里有哪些关于人的数据

**这个软件保存的是它并不拥有的那些群里，成员的数据。** 运行它的人手上握着一批记录，
记录里的人从未与他直接约定过什么 —— 他们只是进了一个 Telegram 群，
而那个群的管理员把这个机器人接了进来。

这是首先要知道的事，所以写在最前面。

**不存在唯一的官方实例。** 这是一个开源项目，任何人都可以自己运行一份。
你面对的那一份由谁运行，数据就在谁手上，保存多久由他决定，出了事也由他负责。
本文说明的是**这个软件**做什么，那在每一份拷贝上都一样；
**某一个实例**做什么由运行它的人决定，第 4 节就是留给他填的。

## 1. 它读什么

- **入群申请。** 群开了加入审批之后，Telegram 会把申请发给机器人，
  其中带有申请人的用户 ID、用户名和显示名。
- **成员变动。** 进群、退群、被提为管理员、被限制。
- **它担任管理员的那些群里的消息。** 管理员身份的机器人关闭了隐私模式，
  因此收得到这些群里的全部消息。这些消息用于反垃圾与自动回复，**消息正文不保存**。
- **发给机器人的私聊**，申请人就是这样作答的。

## 2. 它保存什么

下表中的表都来自被检查的 schema migration。
`scripts/check-privacy-tables.py` 会检查全部 migration；如果 schema 新增了带用户
或群标识的表，而本文没有列出该表，检查就会失败。

| 表 | 关于谁 | 存了什么 |
|---|---|---|
| `chat` | 一个群，不是人 | 群的 ID、标题与设置 |
| `challenge` | 申请人 | 用户 ID、群 ID、最终状态与原因、尝试次数、各个时间点、由哪位管理员结算，以及一段 payload：题面、选项、**当时的显示名**、挑战发出时的消息 ID |
| `verification_failure` | 申请人 | 用户 ID、群 ID、失败次数、最后一次失败的时间 |
| `warning_counter` | 群成员 | 用户 ID、群 ID、当前警告数 |
| `rule` | 不直接指向人 | 某个群的题目、回复与过滤规则 —— 管理员若自己在里面写了名字，那就有 |
| `pending_action` | 申请人或群成员 | 机器人就某一次挑战将要做、尚未做完的动作：动作本身、重试次数、上一次的错误。它不直接写用户 ID，而是指向一条 `challenge`，那条记录的 id 形如 `chat:user:nonce`，两个标识就编在里面 |
| `verification_observation` | 涉及成员关系变更时是申请人或群成员；其他动作不指向任何可识别的人 | 被抑制的操作及其时间。批准、拒绝、封禁、解封、禁言和解除禁言还会保存群 ID 与用户 ID。它不保存消息正文、通知正文、callback ID 或答案、挑战答案以及 Telegram 消息 ID |

三张表不含个人数据：`agent_tally` 统计挑战里那道埋伏中，对方自称的模型名；
`verification_runtime` 存两个数字；`update_poll_lease` 记录当前是哪个进程在从 Telegram 读取更新。

**它不保存**：消息正文、手机号、电子邮件地址、IP 地址、位置，
以及任何 Telegram 没有随上述事件一并发来的字段。它不读取自己不是管理员的群里的消息；
Telegram 的秘密聊天不经过机器人，因此不在其中。

## 3. 保存多久

- **挑战记录**在结算之后仍然保留，因为操作记录正是管理员查看经过、
  以及撤销一次误判的依据。
- **失败计数**就是冷却期本身，随冷却期到期而失效。
- **警告**保留到被清除，或被上限驱逐。
- 机器人被移出某个群，或管理员在控制台删除该群数据之后，该群的记录被清除。
- **只观察模式的成员关系变更记录**随对应群的数据一并清除。
  不含标识的操作与时间记录会继续保留，供切换前后对比。

某个实例可以比这保存得更短。要保存得更长，就得改代码。

## 4. 运行实例的人要自己决定并写明的

把这一节抄进你自己实例的页面并填好。留空本身也是一种回答，而且不是个好回答。

- **这个实例由谁运行**，怎么联系。
- **数据库在哪里** —— 哪台机器，哪个国家。
- **谁能进控制台**，也就是谁能看到上面那些记录。
- **日志保留多久。** 日志与数据库是两回事，见第 5 节。
- **有没有把数据给别人。** 软件本身不会给出去，运行它的人可以。
- **怎么要求删除自己的记录**，以及需要多久。

## 5. 日志

机器人会写运行日志。日志里**带用户 ID 和用户名** ——
一行形如 `join 8913270020 (@someone) in group -100…` ——
以及当时判定了什么、依据是什么。日志里没有消息正文，也没有挑战答案。

日志写到哪、谁能看、留多久，由运行实例的人决定，并写进第 4 节。
用 systemd 安装时日志进 journal，随那台机器的保留策略。

## 6. 如果你是群成员

你面对的是两方，而且通常不是同一批人：

- **你所在群的管理员**选择了使用这个机器人，选定了题目，
  也能看到并撤销它对你所在群做出的判定。
- **运行实例的人**运行着这份程序，数据库在他手上。

先找群管理员 —— 他们可以在控制台删除你在该群的记录。
如果这还不够，他们可以告诉你运行实例的人是谁。

## 7. 如果你在运行一个实例

数据在你手上。这个软件给了你把这件事做得诚实的工具：

- 在控制台删除某个群的数据即清除，界面会写明需要多久。
- 把机器人移出该群，效果相同。
- 第 2 节里的每一项都可核查 —— 那是一份普通的 SQL schema，可以逐行查看。

本文不是法律意见，也不会让你的实例合规于任何法规。
它只是把你手上究竟握着什么讲清楚，而任何诚实的回答都得从这里开始。
