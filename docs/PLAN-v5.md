# v5 方案计划书

从单体机器人改造为「一个机器人服务多个群 + Web 控制台」。
**本文件规定做什么、按什么次序做、以及每步做完的判据。** 其余依据：

| 要查什么 | 看哪份 |
|---|---|
| 界面取值、屏的内容、文案规则 | `web/design.html` |
| 包结构、数据、流程、稳定性 | `web/architecture.html` 或 `docs/ARCHITECTURE.md` |
| 构建、提交、PR 前检查、代码风格 | `CONTRIBUTING.md` 与 `docs/development.md` |

## 0. 目标与范围

### 语言

提交信息用英文。`README.md` 用英文，另给 `README.zh-CN.md`。
面向使用者的文档与界面文案用中文，过书写检查。代码注释用英文。

### 全程禁止面条

**每一次改动都按完整架构落地，不允许先塞进去以后再整理。**
文件 600 行、函数 80 行、圈复杂度 15 是硬性上限，一次提交只涉及一组职责。
新代码必须落在架构书已声明的包里；需要新包时先改架构书。
禁止出现 `util`、`common`、`helper`、`misc` 这类无边界的包。

上限是触发讨论的阈值，不是可以逼近的目标。**接近上限时先问是不是分错了包。**
细则见 `docs/ARCHITECTURE.md`，检查在阶段零建立。

### 要达到的

1. 任何人把机器人拉进自己的群即可使用，由该群的 Telegram 管理员自行配置。
2. 有 Web 控制台，覆盖当前 Telegram 面板与配置文件里的每一项设定。
3. 状态在数据库，并发与重启之下不丢、不重复结算。
4. 一条命令部署，升级失败自动回退。

### 功能范围

这一轮要做的功能，按屏列出。每一项的界面规定见 `web/design.html`，
结构规定见 `docs/ARCHITECTURE.md`。

| 屏 | 内容 |
|---|---|
| 首页 | 四层：概况四个数字、需要注意、近期趋势、常用配置入口 |
| 等待队列 | 正在等待的申请，放行、拒绝、封禁 |
| 验证方式 | 投递渠道与五种挑战类型；被邀请入群三选一；超时、失败上限、封禁时长 |
| 题库 | 规则式题目的增删改、内置模板、试答、三语、导出导入 |
| 反垃圾 | 四条出厂默认规则加自定义规则、分数累加、四档处置、先观察不处置 |
| 免验证来源 | 信任群、必关频道、白名单，查询失败时的方向 |
| 群与频道 | 机器人所在的群、当前群模式、拥有者绑定 |
| 管理与处罚 | 警告上限、反频道马甲、处罚记录去向 |
| 消息与文案 | 自动回复、进出提示、验证全流程文案，留空即用默认 |
| 订阅推送 | RSS 与 Atom 与 JSON Feed、过滤、静默、失败暂停 |
| 统计 | 结果趋势、通过率、各方式拦截量 |
| 诊断 | 权限预检、接口延迟、心跳、一致性检查 |
| 功能 | 能力开关，默认全关，另给两个预设按钮 |
| 偏好 | 标记、名字、强调色、标题图标、保存方式 |

### 五种验证方式

| 方式 | 备注 |
|---|---|
| 入群选择 | **已被攻破**，此备注必须显示在后台的选项旁边 |
| 入群问答 · 输入 | 答案可被检索或传播后失效 |
| 入群问答 · 规则 | 内核版本号一题即此类，靠不存在的诱饵筛选 |
| 工作量证明 | 仅网页。难度按二进制位计，不按十六进制字符计 |
| 人机验证 | 仅网页。依赖外部服务，失败方向需配置 |

条件类型是封闭集合，作用于三处：验证答案、消息文本、显示名与个人简介。
新增一种玩法应当是新增一条配置，不是新增一段代码。

### 不在本轮范围### 不在本轮范围

- 付费与配额计费。
- 移动端原生应用。
- 把 `lookup` 与 `feed` 拆成独立服务。它们保持在同一进程内，仅由每群开关控制。
- 多实例水平扩容的实际部署。数据模型按它设计，但本轮仍单实例运行。

### 验收标准

**删掉我们社区那几行配置，产品照常运转。** 这句话在每个阶段结束时都要能成立。

## 1. 阶段划分

六个阶段，一个阶段一个分支一个 PR。**上一阶段合入 `next` 之前不开始下一阶段。**
每阶段结束时线上可发布，不存在「做到一半的中间态」。

| 阶段 | 分支 | 内容 | 预计改动量 |
|---|---|---|---|
| 零 | `v5/gates` | 先立尺子：行数、复杂度、包边界检查与基线清单 | 新增约 300 行脚本与配置 |
| 一 | `v5/split-verify` | `service.go` 同包纯移动 | 移动 2859 行，新增 0 |
| 二 | `v5/ports` | 抽出 `Gateway` 与 `Store` 接口 | 新增约 200 行，改动约 400 行 |
| 三 | `v5/dbutil` | 数据层换数据库，含待执行动作表 | 新增约 1400 行，删除 JSON 持久化 |
| 四 | `v5/config` | 配置换 `configupgrade`，分三层 | 新增约 400 行，删除版本链 |
| 五 | `v5/rules` | 规则引擎独立成纯函数包，含归一化与结构信号 | 新增约 600 行 |
| 六 | `v5/console-core` | 契约、接口层、认证、前端骨架、一条通路 | 新增较多，独立目录 |
| 七 | `v5/console-screens` | 其余各屏 | 按屏推进 |
| 八 | `v5/multitenant` | 去掉全局默认，配置按群隔离 | 改动配置读取路径 |

### 阶段零 · 先立尺子

**分支** `v5/gates`

在任何实质改动之前，把度量与边界检查建起来。**没有尺子的上限只是一句话。**

| 检查 | 内容 |
|---|---|
| 文件行数 | 超过 600 行即失败，列出超限文件与行数 |
| 函数行数 | 超过 80 行即失败 |
| 圈复杂度 | 超过 15 即失败 |
| 包边界 | 验证包不许引用 telego；规则包不许引用数据库与网络 |
| 中文 | 面向使用者的文案过书写检查 |

**当前的树必然超限**，`internal/verify/service.go` 就有 2859 行。
因此这一阶段同时建立一份基线清单：把现有超限项逐条列出并冻结，
**只禁止新增和恶化，不要求一次修完**。每个后续阶段消掉自己范围内的那几条。

**每条检查都要执行到红再改回绿**，做法见工作流第 06 节。

**验收**：`make lint` 可执行；故意把一个文件写到 601 行时它变红，
且红在行数检查那一条上；基线清单里的每一项都能追到具体文件与行数。

**不做**：不在这个阶段修任何超限项。建尺子与用尺子分开。

### 阶段一 · 同包纯移动

**分支** `v5/split-verify`

`internal/verify/service.go` 现为 2859 行，混合七组职责。按职责拆成多个文件，
**包名不变、签名不变、行为不变**。

| 新文件 | 承载 |
|---|---|
| `service.go` | 结构体定义与构造 |
| `join.go` | 入群申请处理 |
| `answer.go` | 答案判定 |
| `settle.go` | 批准、拒绝、封禁 |
| `timeout.go` | 超时与恢复 |
| `postjoin.go` | 进群后验证 |
| `notify.go` | 消息发送与清理 |

**不做**：不改任何函数签名；不拆锁；不移动测试文件；不夹带缺陷修复。
发现缺陷记进 issue，本阶段不动。

**验收**
```
git diff --stat        # 只有移动，新增删除行数相抵
gofmt -l .             # 空
go build ./... && go build -tags gentoo ./...
go test -race ./... && go test -race -tags gentoo ./...
```

**风险**：`v.mu` 是跨文件共享状态的边界。按新文件拆锁会引入死锁，本阶段一律不动锁。

### 阶段二 · 抽出接口

**分支** `v5/ports`

新增 `internal/verification/ports.go`，定义 `Gateway`、`Store`、`Clock`。
现有实现原样满足接口，不改行为。

**关键约束**：接口定义在使用方。`verification` 声明它需要什么，
由 `telegram` 与数据层实现。此后 `verification` 包不再引用 telego。

**验收**：行为零变更；新增假实现的单元测试，覆盖批准、拒绝、超时、重复到达四条路径；
`grep -r telego internal/verification` 无结果。

### 阶段三 · 数据层

**分支** `v5/dbutil`

引入 `go.mau.fi/util/dbutil`，建立 `migrations/00-latest.sql`，
把现有 JSON 状态一次性迁入数据库。表结构见 `docs/ARCHITECTURE.md` 第 3 节。

**必须同时落地的三件事**，缺一则本阶段未完成：

1. `challenge_open` 部分唯一索引，重复到达在数据库层被拒绝。
2. 所有状态转换改为带条件的更新，影响 0 行按已结算处理。
3. 超时由扫描器领取到期记录，删除进程内定时器。

**迁移**：提供一次性导入命令，可重复执行且结果一致。
导入前备份原 JSON 文件，导入后校验条数与关键字段。

**验收**：迁移可重放；旧二进制连新库被拒绝启动；
用旧数据跑一遍导入，等待队列与操作记录条数与导入前一致。

### 阶段四 · 配置

**分支** `v5/config`

换 `go.mau.fi/util/configupgrade`。现有 schema v1、v2、v3 折叠成一组
「旧路径 → 当前路径」复制规则，删除逐版本分支。
新增 `internal/settings/defaults.yaml`，完整带注释。

**验收**：准备三份分别为 v1、v2、v3 的真实配置文件，各跑一次升级，
确认用户改过的值全部保留，新字段取默认值。

**已知代价**：拼错但语法合法的未知键会在写回时消失。
评审要求每个 struct 字段同时具备示例项与复制规则。

### 阶段五 · 规则引擎

**分支** `v5/rules`

把匹配相关的代码抽成 `internal/rules`，**纯函数、无副作用、禁止导入数据库与网络**。
包含归一化流水线、封闭的条件类型集合、结构信号计分。

**为什么单独一个阶段**：控制台的试答要直接调用它。
它若带副作用，试答就只能另写一份，而另写的那份迟早与线上判定不一致。

**验收**：该包的导入列表中没有数据库与网络相关的包；
用真实垃圾样本跑测试，断言归一化之后能命中；试答与线上判定走同一个函数。

### 阶段六 · 控制台骨架

**分支** `v5/console-core`

**次序固定**：先定契约，再写后端，再写前端。契约先定，两端各自对着它开发。

先做能走通一条路径的最小集：**登录 → 选群 → 看等待队列 → 放行一个人**。
这条通了再铺其余屏。

同时落地的还有：Mini App 身份校验、写入前现查管理员、权限定时同步、
前端目录约定与错误边界。

**验收**：契约生成物与手写代码无差异；前端在没有后端时能对着假数据启动；
一条命令部署后健康检查通过。

### 阶段七 · 其余各屏

**分支** `v5/console-screens`

按屏推进，一屏一个提交。每屏做完对照 `web/design.html` 检查取值。

**不做**：不在这个阶段改接口契约。需要改契约就回到阶段六的分支。

### 阶段八 · 多租户

**分支** `v5/multitenant`

去掉「全局默认 + 每群覆盖」，改为「出厂默认 + 每群取值」。
配置读取路径统一走 `Store.Settings(chatID)`。

**验收**：把我们社区的群配置全部删除，机器人与控制台照常工作；
`grep -rn '主群\|mainGroup\|isMainChat' internal cmd` 无业务分支。
